# Bug log

Every bug found while building and testing the game, with its symptom, root cause and fix.

## 1. Test wrongly expected the AI to never fire into a boxed-in corner

- **Symptom:** The unit test `skips cells where the smallest remaining ship cannot fit` failed: the AI fired at the boxed-in corner cell on its 43rd shot. The test expected that never to happen before shot 90.
- **Root cause:** The bug was in the test, not the AI. With spacing 3, every 3-cell segment on the board contains at least one hunt-pattern cell. Once all ~33 hunt-pattern cells have been fired at and missed, no length-3 ship fits anywhere. At that point the AI correctly falls back to any unknown cell, and the corner is one of them.
- **Fix:** The test now checks only the first 25 shots, while hunt-pattern cells that could still hold a ship remain. The fallback behaviour is intentional and is documented in `pickHunt`.

## 2. "Neighbouring ship" test never actually exercised adjacent ships

- **Symptom:** The test `finishes off a neighbouring ship that it hit while sinking another` failed. The AI went back to hunt mode before the second ship was sunk.
- **Root cause:** A test scenario bug. The AI's first probe after hitting the destroyer went along the destroyer, sank it, and returned to hunt mode (correctly, since it had no hits left to follow up). It never hit the cruiser underneath, so the scenario it was meant to test never happened.
- **Fix:** The test now feeds the AI a hit on the destroyer, then a hit on the cruiser directly below it, which looks like a single vertical ship. It then asserts that the AI stays in target mode until both ships are sunk, over 50 random seeds.

## 3. Type-check failed after a move changed the game phase

- **Symptom:** `npm run build` failed with `TS2367: This comparison appears to be unintentional because the types '"player-turn"' and '"ai-turn"' have no overlap` in `src/main.ts`.
- **Root cause:** `onEnemyBoardClick` first checks `game.phase !== 'player-turn'`, so TypeScript narrows `game.phase` to `'player-turn'`. It doesn't know that `game.playerFire()` then changes the phase, so it flagged the later `game.phase === 'ai-turn'` / `'won'` checks as impossible. `aiTurn` had the same problem. A local variable annotated as `Phase` didn't help, because TypeScript narrows on assignment too.
- **Fix:** Added a small `currentPhase(): Phase` helper. Reading the phase through a function call gives back the full `Phase` type after each move.

## 4. After a defeat, the revealed enemy fleet couldn't be inspected

- **Symptom:** Found during browser testing. After losing, the enemy's surviving ships were drawn on the board, but the win/loss dialog darkened and blurred the whole board and covered the middle cells. Escape and clicking the backdrop did nothing, and the dialog's only button, **Play again**, wiped the board. This was worst on mobile.
- **Root cause:** `showResult()` always opened a full-screen overlay with `backdrop-filter: blur(3px)`, and nothing could close it except starting a new game.
- **Fix:** The dialog now has a **View board** button, and Escape or clicking the backdrop also closes it. A game-over bar with the result and its own **Play again** button stays above the boards, so you can look over the final board and then start a new game.

## 5. Enemy fleet placement could be rigged from the browser console

- **Symptom:** Found in a security audit of the production build. Typing `Math.random = () => 0` in the browser console and then pressing **Play again** gave an enemy fleet whose layout was fully predictable. A player could work out every ship position without firing a shot. (The AI's choices could be rigged the same way.)
- **Root cause:** `Game` and `BattleshipAI` used `Math.random` as their default random source and looked it up on every call. Pages can't make built-in globals read-only, so a player could replace it with any function they liked.
- **Fix:** `src/game/random.ts` now exports `defaultRng`. It keeps references to `crypto.getRandomValues` (or `Math.random` if that isn't available) that it grabs when the module first loads, so replacing either one from the console later does nothing. `Game` and `BattleshipAI` use it by default. A new test replaces `Math.random` and checks that new games ignore it. `vite.config.ts` now sets `build.sourcemap: false` explicitly, so readable source is never shipped.
- **Audit of the rebuilt production build, which passed:** loaded it from `vite preview` in Chrome, randomized the fleet and started a battle. Results: no new properties on `window`; enemy cells only expose `cell`/`target` classes, `aria-label="unknown"` and `data-row`/`data-col`; localStorage, sessionStorage and cookies are all empty; no source map is published; `import('/battleship-ai/src/game/game.ts')` fails because only the bundled module is served. The game code runs inside that one module and exports nothing, so the console has no handle on the game state. During earlier testing the enemy positions were read by importing `/src/game/game.ts` from the Vite **dev** server, and that only works on the dev server.
- **Limit:** the game is static, so the enemy fleet has to live in the browser's memory. Someone stepping through the script with the DevTools debugger can still find it. Only a server could prevent that, and the brief rules out a backend.

## 6. Moving a placed ship made it jump and look shorter

- **Symptom:** Found while play-testing the live site. After **Randomize**, clicking a placed ship to move it made the ship jump down or right on its own. If the jump pushed it past the edge of the board, it showed fewer cells than its real length. For example, clicking the stern F10 of a Carrier at F6–F10 left a single red cell, and the ship couldn't be dropped there.
- **Root cause:** `pickUp` in `src/main.ts` stored the clicked cell as `hover`. The preview and the next drop then used `hover` as the ship's bow (the `origin` given to `shipCells` / `placePlayerShip`). So the ship moved forward by the position of the clicked cell within the ship. The preview also drew only the cells still on the board, so a ship pushed past the edge looked shorter. The model was never wrong: `Board.place` always places the full `spec.length`, so the fleet stayed 5, 4, 3, 3, 2.
- **Fix:** `main.ts` now records `grabIndex`, the cell of the ship that was clicked. The new `heldShipOrigin` in `src/game/placement.ts` uses it to work out the bow, so that cell stays under the cursor. Picking a ship up leaves it exactly where it was, rotating turns it around the grabbed cell, and the held ship slides back onto the board instead of hanging off the edge. That means the preview always shows the full ship. New ships from the picker are still held by the bow. `tests/placement-ui.test.ts` loads the real page in jsdom. It picks up every ship by every one of its cells, drops it back, and checks it lands in the same cells. It also moves ships into each corner and rotates them, checking the preview always has full length and the fleet stays 5, 4, 3, 3, 2. Both UI tests fail without the fix.

## 7. Clicking a red (invalid) spot swapped the ship you were placing

- **Symptom:** Reported from play-testing. Place the Carrier, then hover the Battleship over it. The preview correctly turns red, but clicking there anyway lifted the Carrier back off the board and selected it instead of the Battleship. It looked as if the Battleship had been dropped somewhere wrong and the game had moved on.
- **Root cause:** `onPlayerBoardClick` in `src/main.ts` had a fallback for failed drops: if a ship was already on the clicked cell, it called `pickUp` on that ship. That fallback ran even while you were still holding another ship, so a click on an invalid spot swapped the selection instead of doing nothing.
- **Fix:** A failed drop now only moves the preview to the clicked cell and shows a message. The ship you are holding stays selected and keeps following the cursor until you click a valid (green) spot. Clicking a ship on the board still picks it up when you aren't holding one, and the ship picker can still switch ships at any time. `Start battle` stays disabled until all five ships are placed. A new test in `tests/placement-ui.test.ts` plays exactly this sequence on the real page in jsdom, and it fails without the fix.

## 8. UX bug: the next ship's preview started on top of another ship

- **Symptom:** Reported from play-testing, and worst on mobile. After you placed a ship, the next ship's preview appeared on the cell you had just tapped, so it sat on top of the ship you had just placed and showed red. A fresh game showed no preview at all until the cursor moved. A touch screen has no cursor to move the preview away, so you had to guess where to tap.
- **Root cause:** Selecting the next ship (`selectNextShip`, the ship picker, `newGame`) changed `selectedId` but never moved `hover`. The preview stayed on the last clicked cell, or stayed empty when `hover` was `null`.
- **Fix:** All three now go through a new `selectShip` in `src/main.ts`. It moves the preview to `firstFreeSpot` (in `src/game/placement.ts`): the first cell, scanning rows then columns from the top left, where the ship fits on the board without overlapping, in its current orientation. If it fits nowhere that way, it tries the other orientation and turns the ship to match. Picking up a ship already on the board still leaves its preview where the ship was. New tests in `tests/placement-ui.test.ts` place the whole fleet using only taps on the previewed cells, with no hover, and check that every preview starts green on the expected first free spot. They also cover the ship picker and **Clear**, and there are unit tests for `firstFreeSpot`, including the orientation fallback. The UI tests fail without the fix.

## 9. Follow-up to #7: earlier clicks and the cursor position carried over to the next ship

- **Symptom:** Reported from play-testing as a follow-up to #7, whose fix turned out to be incomplete. Place the Carrier, click the Battleship on a red spot over it (nothing happens, which is correct), then click a valid empty spot (the Battleship is placed). The Cruiser then appeared straight away in solid green next to the earlier red spot (F1–H1 after a red click at C1), away from the cursor, before any click. It looked as if it had been placed on its own. Reproducing it in Chrome with a real mouse and real touch taps showed two more ways an earlier input reached the next ship. When a tap fired twice, or with a mouse double-click, the second click hit the ship that had just been selected. That ship went red at the cell just used, and a "would overlap" error showed before you had touched it. Also, moving the mouse within the cell you had just clicked didn't move the preview, because the cursor never left that cell.
- **Root cause:** #7 only changed what a failed drop does. It didn't change which clicks count as drop attempts or where the next preview appears. `BoardView` in `src/ui/boardView.ts` passed every `click` straight to `onPlayerBoardClick`. It never checked whether that click came from a new press, so a repeated click from a press made before the placement was handled as the next ship's first drop. `selectShip` in `src/main.ts` (#8) always put the next preview on `firstFreeSpot`, even with a mouse over the board. The board didn't track where the mouse actually was, so the preview jumped away from the cursor.
- **Fix:** `BoardView` now numbers pointer presses and links each click to the press that started it. For the second click of a double-click or double-tap, that is the first press. A keyboard click counts as a press of its own. After a successful placement, `onPlayerBoardClick` calls `playerView.ignoreEarlierPresses()`, so a click from any earlier press is dropped and the next ship needs a new press. `BoardView` also tracks `mouseCell`, the cell under the mouse. `selectShip` starts the next ship's preview there when the mouse is on the board. With touch, or with the cursor off the board, it still uses the first free spot from #8. Everything from #7 still works: a red click does nothing, the held ship stays selected, and **Start battle** stays disabled until all five ships are placed. New tests in `tests/placement-ui.test.ts` play the reported sequence with real `pointerenter`/`pointerdown`/`pointerup`/`click` mouse events and with `pointerdown`/`touchstart`/`touchend`/`click` taps. They cover a double-click and both kinds of tap fired twice: a repeated click with no new press, and a full second tap. The new tests fail without the fix. The fix was also checked in Chrome with real mouse input and touch emulation.
